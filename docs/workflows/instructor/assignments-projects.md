# Instructor workflow — assignments and projects

**Assignments** and **projects** are the primary vehicles for **sustained coding work**: multiple files, iterative runs, and rich version history.

## Pedagogical intent

- Students learn through **draft → run → revise**.
- You want **moderate** integrity signals: enough to deter misconduct and explain anomalies, without pretending to replace human judgment.

## Configuration checklist

- [ ] Activity type set to **assignment** or **project** (as your product enumerates).
- [ ] **Tracking level**: typically **moderate** (see [matrix](../../reference/activity-types-matrix.md)).
- [ ] **Starter template** includes clear success criteria (`ASSIGNMENT.md`).
- [ ] **Due date** communicated (product + syllabus).
- [ ] **Late policy** stated in syllabus; link or paste key rules in instructions.

## Delivery workflow

1. Upload template files (single file or multi-file).
2. Enroll students.
3. Optionally announce **transparency**: what is logged (saves, runs, edits summary).

## Review workflow

1. Open **submissions list** for the activity.
2. For each student, review **files**, **timeline** (history of commits/saves), and **run logs** (per deployment policy).
3. Compare against rubric; document anomalies using institutional process.

## Integrity notes

- Encourage students to **cite** permitted resources in comments when collaboration rules allow inline citations.
- Run logs show **execution attempts**, not proof of authorship alone—pair with timeline and assessment design.
